What this book is

This is a book about one tiny, broken program, and all the ways it can fail.

It's built around the Hell in a Cell Kata: a Hello, World! in Rust, deliberately riddled with defects, guarded by a continuous integration workflow that won't let any of them slide. Your job is to make the checks go green. The checks don't care about your feelings.

The book comes in four parts:

  1. Before the Bell. This part. Why the cell, why Rust, the rules of the match, and how to set up your corner.
  2. The Kata. The broken code, file by file, with enough explanation to know what each piece is for, and no hints about what's wrong with it. This is where you put the book down and fight.
  3. The Fight, Round by Round. The solution, one fix per commit, in the order the referee reports the failures. Every intermediate state is real: each round is a tagged commit you can check out, and the error message printed in each chapter is the one the compiler actually gave, checked every time this book is built.
  4. Man vs. Machine. The same kata, handed to AI coding agents. What they fixed, what they missed, and what that tells you about working with them.

The Cell

You and your AI opponent will be locked inside a cell built from the Rust programming language.

Why Rust?

Because it's difficult, and cruel, and the programmers who code in it are all assholes. Naturally, since I am an asshole, it's my favorite language.

Seriously, though: because of its strict nature, it's the perfect antidote to the AI vibe sludge coming out these days. Rust doesn't let anything slide. Other languages let you get away with things, and the bill comes due in production, at 3 a.m., on a holiday weekend. Rust sends the bill before the code ever runs:

  • The compiler refuses to build code whose types don't line up, and it explains itself better than any compiler you've ever used.
  • Clippy, the linter, has hundreds of opinions about how Rust ought to be written, and in pedantic mode, it shares all of them.
  • rustfmt settles every formatting argument, for everyone, forever.
  • rustdoc compiles and runs the examples in your documentation, and checks that every link in it points at something that exists.

Each of those is a judge. Put them all in a CI workflow with warnings turned into errors, and you get a cell that nobody, human or machine, can talk their way out of.

Why Hello, World!?

The problem is simple: Hello, World!. Yes, Hello, motherfucking World!: the most overused programming exercise on the planet, beaten so hard it's turned into the finest McRib-worthy pink slime.

That's the point. There's no algorithm to get lost in, and no domain to learn. Everybody knows what the program should do, so every bit of your attention goes to how it's broken. And there's a lot of broken packed into thirty-three lines.

Where it came from

The kata started life as The World's Simplest Kata: a quick way to check that a new Rust setup could build, test, lint, and format. Break a few things on purpose, and it doubles as a tour of every gate a Rust project should have. Break a few more, and it's a cage match.

Katas

A kata is a small exercise, meant to be repeated until the moves are automatic. The word comes from martial arts, where a kata is a choreographed sequence practiced alone until it's reflex.

Rules of the Match

The mission

  1. Fork the kata.
  2. Make the failing GitHub Actions green.
  3. ...
  4. Profit!

That's it. There's no spec to read and no feature to build. The program should print Hello, world!, and every check in the CI workflow should pass.

The rules

Win the way the referee counts. Green means green on GitHub, on every job, on every compiler in the matrix. "It works on my machine" is a forfeit.

No bribing the referee. Deleting a failing test, sprinkling #[allow(...)] over the lints, or removing a job from the workflow will turn the checks green. It doesn't count. If a check is wrong, you can fix the check, but you have to be able to explain why it was wrong.

No outside help, the first time through. Not a search engine, not a chatbot, not a friend. The compiler, the tools, and their documentation are fair game; they're what you'll have on the job. Part IV is where the robots get their turn.

Time yourself. Not to race anyone. Just so that, when you read Part IV, you have a number to compare with.

How to read this book

  • Part II is safe. It walks through the kata's files and explains what each piece of Rust is for. It doesn't tell you what's broken. Each chapter ends with a bit of 🥊 Corner Advice: a nudge, not an answer.
  • Part III is the spoiler. Read it after you've finished, or after you've truly given up. It fixes one thing per round, in the order the referee reports them, and explains both the fix and the wrong fixes that are easy to reach for.
  • Part IV is the payoff. Once you know every defect, you can score the machines.

Reading the tape

The Cargo Book has the full list of keys. The ones worth your attention here:

  • edition — Rust ships breaking changes to the language in editions: 2015, 2018, 2021, and 2024. An edition is an opt-in contract. Code written for 2015 still compiles today, because it says it is 2015 code.
  • rust-version — the oldest compiler this crate promises to build on, also called the Minimum Supported Rust Version, or MSRV. It's a promise to your users, and Cargo holds you to it.
  • license — an SPDX identifier. It should agree with the LICENSE file sitting at the root of the repo.
  • [lib] and [[bin]] — this one package builds two things: a library that holds the code, and a binary that calls it. The single brackets on [lib] and the double brackets on [[bin]] are not a typo. A package can have at most one library but any number of binaries, and double brackets are TOML's way of saying "an array of these."
  • [lints.clippy] — lint configuration that lives in the manifest instead of scattered through the source. pedantic = "warn" turns on Clippy's pedantic group. More on Clippy when we meet the referee.

The Library

This is where the fight is. Thirty-three lines of Rust that do one thing: say hello. Read all of it before you read a word of what follows.

pub struct Hello;

/// The [Helo] project is a simple hello world program. It comes with two methods:
///
/// 1. `hello` - This method takes a `String` and returns `Hello, {name}!`.
/// 2. `hello_world` - A default method that returns `Hello, world!`.

    }
}

    use super::*;

    #[test]
    fn hello_world() {
        assert_eq!("Hello, world!", Hello::hello__world());
    }
}

Anatomy of a Hello

Top to bottom, here's what each piece is for. Whether each piece actually does its job is your problem.

A unit struct

pub struct Hello;

A struct with no fields. It holds no data and takes up no memory. It exists only to give the functions below a name to hang off of, so that callers write Hello::hello(…). Plenty of Rust code would use free functions here instead. This is a stylistic choice, not a bug.

Doc comments

Lines that start with /// aren't comments to the compiler — they're documentation, and they belong to whatever item comes right after them. cargo doc turns them into the HTML pages you've seen on docs.rs. They're Markdown, and they have two superpowers most documentation doesn't:

  1. Intra-doc links. Put an item's name in square brackets — [Hello] — and rustdoc turns it into a link to that item's page. It resolves the name, the same way the compiler would.
  2. Doc tests. A fenced code block inside a doc comment is compiled and run by cargo test, as if it were a little program of its own that uses your crate from the outside. Documentation that is also a test is documentation that can't quietly go stale.

The impl block

impl Hello { … } attaches two associated functions to Hello. Neither takes self, so they're called on the type, not on a value: Hello::hello(…), not some_hello.hello(…).

Two kinds of string

Look at the signatures. One function speaks String; the other speaks &'static str. Rust has more than one kind of string, and the difference is the first real bruise every newcomer takes.

  • A String is owned. It lives on the heap, it can grow, and whoever holds it is responsible for it. It's the extra suitcase you check on a trip so you have room for the junk you pick up along the way.
  • A &str is a borrowed view of some text that lives somewhere else. It's the key to the gas station restroom, chained to an old license plate. You can use it, but it's not yours.
  • &'static str is a borrow that lasts for the entire run of the program. String literals — anything you type between double quotes — are &'static str, because they're baked right into the binary. That's the tattoo you got that one night. It's not going anywhere.

Keep those three in your head. You'll need them.

format!

format! works like println!, except it hands you back a String instead of printing it. The {} is a placeholder, filled in by the arguments that follow.

The test module

#[cfg(test)]
mod tests {

#[cfg(test)] means this module only exists when compiling for cargo test; it's stripped out of your real build. use super::*; pulls in everything from the file above it, and #[test] marks a function the test runner should call. assert_eq! panics — failing the test — if its two arguments aren't equal.

The Binary

The library does the work. The binary is the ring announcer: it steps up to the microphone and says what the library tells it to say.

💾 src/main.rs · L1–L5 · step 002 of hellbook · diff · browse

use worlds_simplest_kata::Hello;

fn main() {
    println!("{}", Hello::hello__world());
}

$> git checkout step-002-kata

Two crates, one package

Remember the [lib] and [[bin]] sections of the manifest. Both are named worlds_simplest_kata, and they're compiled as two separate crates. The binary doesn't get to peek inside the library. It has to use it by name, exactly as any other crate on crates.io would, and it only sees what the library marks pub.

That is why this split is worth the extra file. Your binary is the first customer of your library's public API. If the API is awkward, main.rs is where you'll feel it first.

fn main() is where the program starts. println! prints a line to standard output, filling {} with whatever comes after the comma.

🥊 CORNER ADVICE: When you change the library, the binary doesn't get a vote. It either keeps compiling or it doesn't. Keep it in mind every time you change a signature.

The Referee

You don't win this match by deciding you've won. You win when the referee raises your hand, and the referee is GitHub Actions. Every time you push, it checks out your code on a fresh machine it doesn't care about, runs the same commands it always runs, and tells you whether you're done.

It doesn't care how the code looks on your laptop. It doesn't care that it "works on my machine." That is the entire point of continuous integration.

The rulebook

on: — when the referee shows up. Here, on every push and every pull_request.

env: RUSTFLAGS: -Dwarnings — set once at the top, so it applies to every job. -D warnings means deny warnings: anything the compiler would normally just grumble about becomes a hard error. Hold onto that one. It's the single most important line in this file, and it isn't set on your laptop.

jobs: — four judges, each scoring a different part of your fight. They run in parallel, on separate machines, and all four have to raise your hand:

JobCommandWhat it judges
testcargo test --allDoes it compile? Do the unit tests pass? Do the doc tests?
clippycargo clippy -- -Dclippy::all -Dclippy::pedanticIs the code idiomatic, by the pickiest standard Clippy has?
fmtcargo fmt --all -- --checkIs it formatted the way rustfmt would format it?
doccargo doc --no-deps --document-private-itemsDoes the documentation build cleanly, with every link resolving?

strategy: matrix: — the test job doesn't run once. It runs once for every entry in rust: [stable, 1.85.0]: once on the newest stable compiler, and once on 1.85.0. Two fights, same card. You have to win both.

if: — a job with an if: only runs when its condition is true. Two of the four judges have one. Read it closely, and think about who it lets in.

dtolnay/rust-toolchain — a widely used action, by David Tolnay, that installs whatever Rust toolchain you ask for, plus components like clippy and rustfmt.

The four judges, briefly

Tests. The Rubicon of builds. A team that stops keeping its tests green "because we don't have time" might as well hand its keyboards to the robots. Good unit tests are an army of regression testers, ready to descend on your code every time you push.

Clippy. No, not that Clippy. Rust's linter, and the best one in the business. Linting is static analysis that flags code the compiler accepts but a senior engineer would squint at. The kata dials it up to eleven, with pedantic and every warning denied.

Fmt. It seems trivial. Then two people on a team with different editor settings touch the same file, and every pull request turns into a three-hundred-line diff of whitespace. rustfmt settles the argument once, for everybody, forever.

Doc. Rust treats documentation as code: links are resolved, examples are compiled, and with -D warnings, a broken link breaks the build. That ends the oldest standoff in software — stakeholders demanding documentation, developers pointing out it's wrong the day it ships.

Round 1: The Manifest

Last warning. From here on, everything is a spoiler.

The first thing any fighter does is try the obvious move: build it.

$ cargo check · step 002 of hellbook

error: failed to parse manifest at `Cargo.toml`

Caused by:
  rust-version 1.72.1 is incompatible with the version (1.85.0) required by the specified edition (2024)

We haven't even reached the code. Cargo refuses to read the manifest.

It's insane how good the Rust toolchain is at spelling out exactly what's wrong. edition = "2024" needs at least Rust 1.85.0, the release that stabilized the 2024 edition. Meanwhile, rust-version = "1.72.1" promises that this crate builds on a compiler that doesn't even know the 2024 edition exists. Both claims can't be true, so Cargo won't go any further.

The wrong fix

The tempting fix is to set rust-version to whatever you happen to have installed. Run rustc --version, see 1.98.1, type it in, and watch the error go away.

It goes away on your laptop. Then you push, and the referee disagrees. Look at the test matrix again:

      matrix:
        rust: [stable, 1.85.0]

Round 2: The Types

E0308, mismatched types. The first real punch, and it lands on the thing everyone warned you about: strings.

pub fn  hello__world() -> &'static str {
    Hello::hello("wirld!".to_string())
}

hello__world promises to return a &'static str: a borrow of text that lives for the whole program. What it actually returns is whatever hello returns, which is a brand-new, owned String, built at runtime by format!.

A String made inside a function can't be lent out as &'static str. It doesn't live forever; it doesn't even live past the end of the function unless somebody takes ownership of it. The signature is writing a check the body can't cash.

Don't take the compiler's advice

The compiler offers a suggestion:

help: consider borrowing here
   |
21 |         &Hello::hello("wirld!".to_string())
   |         +

Take it, and you get a new error, E0515: cannot return reference to temporary value. The String that hello built is dropped the moment hello__world returns, and a borrow can't outlive the thing it borrows. The compiler is fixing the line it's looking at, not the design you're stuck with. Remember the warning in HINTS.md: the compiler suggestions don't always work.

Three ways out

  1. Return a literal. Make hello__world return "Hello, world!" directly. It's genuinely &'static str, and it compiles. But now there are two copies of the greeting format, and the day someone changes hello, hello__world silently won't follow.
  2. Leak it. Box::leak(…) turns a String into a &'static str by never freeing it. It's a real tool for real problems. This isn't one of them.
  3. Tell the truth. The function returns a String, so say so.

Round 3: The Name

hello__world has two underscores. Rust names functions in snake_case: all lowercase, words separated by one underscore. The compiler's non_snake_case lint flags anything else.

Did you know a double underscore is called a dunder? I learned that at a Central Ohio Python Users Group meeting. Python is full of them — __init__ is a "dunder init" — which is exactly why a Pythonista's fingers type them without asking.

Renaming a public function is never a one-file change. There are three call sites: the definition, the unit test, and the binary. Miss one, and you've traded a warning for an error.

Round 6: Clippy

Four errors, and not one of them is a bug. The code works. Clippy's point is that it could be better, and with -Dclippy::pedantic, "could be better" fails the build. Each lint comes with a link explaining itself, and they're worth reading.

must_use_candidate

#[must_use] tells the compiler to warn if a caller throws the return value away. Both of our functions exist only to return a value; they have no side effects. Calling Hello::hello_world(); and ignoring the result is certainly a mistake, so say so.

needless_pass_by_value

hello(name: String) demands an owned String, then only reads it. Every caller has to allocate a String — "world".to_string() — just so hello can borrow it for a moment and drop it.

Borrow instead. name: &str accepts a string literal as-is, and a caller with a String passes &my_string. This is the same lesson as Round 2, from the other side: take borrowed, return owned. Take the loosest type you can work with, and hand back what you built.

uninlined_format_args

Since Rust 2021, format! can capture variables straight from scope: format!("Hello, {name}!"). It's shorter, and the placeholder says what goes in it.

The ripple

Changing hello's parameter is an API change, so every caller changes too: hello_world, and the doc test. The doc comment's prose said hello "takes a String," and that's no longer true. No tool catches a lying sentence, so that's our job.

Round 9: The Referee

Every check is green. Now go back to Part II and reread the referee, the way you'd reread a contract after you've already signed it.

  clippy:
    name: Clippy
    runs-on: ubuntu-latest
    if: github.event_name != 'pull_request'

Clippy and Fmt only run when the event isn't a pull request. Open a PR, and two of the four judges leave the building. Test and Doc score the fight; the two pickiest judges never see it. A pull request with a lint error, or with a formatting mess, gets a green check mark from the referee.

That green check is the whole trap. Somebody — or something — opens a PR, sees it go green, and declares victory. The reviewer sees green and merges it. The red only shows up afterward, on main, when the push-triggered run finally invites the other two judges.

Think about who opens pull requests against a kata. Hold that thought until Part IV.

Close the loopholes

Two changes:

  1. Delete both if: lines. Every judge scores every fight, pull requests included.
  2. --all-targets on Clippy. Plain cargo clippy lints the library and the binary, but not the tests. Test code is still code: it gets read, copied, and trusted. It should meet the same bar.

Rules of Engagement

Now the robots get their turn.

Every AI coding agent on the market will tell you it can fix a broken Hello, World!. So we're going to let them try, under the same rules you fought under, and score them on the same card.

A comparison is only worth something if it's fair and repeatable. Here's the protocol every contender in this part followed. If you run it yourself, and you should, follow it too, so your results can sit next to these.

The protocol

  1. A fresh fork. Each contender starts from the kata exactly as delivered: the step-002-kata tag in the companion repository, or a new fork of the original. No leftover target/ directory, and no hints in the history.

  2. The same prompt, word for word. No coaching, no follow-up hints, no "you missed one."

    ✍️ EDITOR: The exact prompt goes here. A suggestion, to keep it honest and minimal:

    This repository's GitHub Actions CI is failing. Make every CI job pass.

  3. One sitting. The agent works until it says it's done. If it asks a question, the answer is always: "Do whatever you think is best."

  4. Whatever tools it has. If the agent can run commands, let it. If it can only read and write files, that's part of what's being measured.

  5. Hands off. The human doesn't edit a single line. What the agent hands in is what gets scored.

  6. Record everything. The transcript, the final diff, the time on the clock, and, where it's visible, the cost.

  7. The referee decides. The result is replayed in this book's repository, on a branch named after the contender, and scored by the same make ci that judged Part III. Every "what the referee said" block in this part is verified, the same way Part III's are.

What the kata teaches about working with agents

✍️ EDITOR: The takeaways, once the results are in. A few candidates Part III already sets up, to keep or throw out:

  1. Give the agent the referee. An agent that can run make ci gets the same layered feedback you did. One that can't is guessing.
  2. The gate is the spec. Whatever the gate doesn't check, the agent has no reason to fix. If it matters, put it in the gate, or review for it yourself.
  3. Audit the referee before you trust the green. A pull request that skips half the judges looks exactly like a pull request that passed them.
  4. Read the diff. Every line. It's thirty-three lines of code, and the machines still got some of them wrong.
